<h1>1. 프로세스 개요</h1>
<ul>
  <li>
    프로그램은 실행되기 전까지는 보조기억장치에 덩어리이지만 메모리에 적재되고 실행하는 순간 해당 프로그램은 <strong>프로세스(process)</strong>가 되며 이 과정을 <strong>프로세스를 생성한다</strong>라고 표현한다.
  </li>
</ul>

<br>

<h2>1-1. 프로세스 직접 확인하기</h2>
<ul>
  <li>
    윈도우에서는 작업 관리자의 [프로세스] 탭에서, 유닉스 체계의 운영체제는 ps 명령어로 확인할 수 있다.
  </li>
  <li>
    사용자가 볼 수 있는 공간에서 실행되는 프로세스를 <strong>포그라운드 프로세스(foreground process)</strong>, 사용자가 보지 못하는 뒤편에서 실행되는 프로세스를 <strong>백그라운드 프로세스(background process)</strong>라 한다.
  </li>
  <li>
    백그라운드 프로세스 중에서도 사용자와 직접 소통할 수 있는 백그라운드 프로세스도 있으나 <strong>상호작용하지 않고 정해진 일만 수행</strong>하는 백그라운드 프로세스도 있는데 이를 유닉스 체계의 운영체제에서는 <strong>데몬(deamon)</strong>, 윈도우 운영 체제에서는 <strong>서비스(service)</strong>라고 부른다.
  </li>
    <ul>
      <li>
        실제로 윈도우 운영체제는 [작업 관리자] 창에서 [서비스]를 선택하여 확인해 볼 수 있다.
      </li>
    </ul>
</ul>

<br>

<h2>1-2. 프로세스 제어 블록</h2>
<ul>
  <li>
    운영체제는 빠르게 번갈아 수행되는 프로세스의 실행 순서를 관리하고, 프로세스에 CPU를 비롯한 자원을 분해하기 위해 <strong>프로세스 제어 블록(PCB; Process Control Block)</strong>을 이용한다.
  </li>
  <li>
    프로세스 제어 블록은 <strong>프로세스와 관련된 정보를 저장</strong>하는 자료 구조이다.
  </li>
    <ul>
      <li>
        프로세스 제어 블록에는 해당 프로세스를 식별하기 위해 꼭 필요한 정보들이 저장된다.
      </li>
      <li>
        PCB는 커널 영역에 생성된다.
      </li>
      <li>
        운영체제도 수많은 프로세스들 사이에엇 PCB로 특정 프로세스를 식별하고 해당 프로세스를 처리하는 데 필요한 정보를 판단한다.
      </li>
      <li>
        PCB는 프로세스 <strong>생성</strong> 시에 만들어지고 실행이 끝나면 <strong>폐기</strong>된다.
      </li>
    </ul>
</ul>

<h3>1-2-1. 프로세스 ID</h3>
<ul>
  <li>
    프로세스 ID(PID; Process ID)는 <strong>특정 프로세스를 식별</strong>하기 위해 부여하는 <strong>고유한 번호</strong>이다.
  </li>
    <ul>
      <li>
        같은 이을 수행하는 프로그램이라 할지라도 두 번 실행하면 PID가 다른 두 개의 프로세스가 생성된다.
      </li>
      <ul>
        <li>
          윈도우에서는 [작업 관리자]창에서 확인이 가능하다.
        </li>
      </ul>
    </ul>
</ul>

<h3>1-2-2. 레지스터 값</h3>
<ul>
  <li>
    프로세스는 자신의 실행 차례가 돌아오면 이전가까지 사용했던 <strong>레지스터의 중간값들을 모두 복원</strong>한다.
  </li>
    <ul>
      <li>
        이전까지 진행했던 작업들을 그대로 이어 실행하기 위해서이다.
      </li>
    </ul>
</ul>

<h3>1-2-3. 프로세스 상태</h3>
<ul>
  <li>
    현제 프로세스가 어떤 상태인지 또한 PCB에 기록된다.
  </li>
    <ul>
      <li>
        예를 들어 입출력장치를 사용하기 위해 기다리고 있는 상ㅌ태인지, CPU를 기다리고 있는 상태인지 등이 해당한다.
      </li>
    </ul>
</ul>

<h3>1-2-4. CPU 스케줄링 정보</h3>
<ul>
  <li>
    프로세스가 언제, 어떤 순서로 CPU를 할당받을지에 대한 정보도 PCB에 기록된다.
  </li>
</ul>

<h3>1-2-5. 메모리 관리 정보</h3>
<ul>
  <li>
    프로세스마다 메모리에 저장된 위치가 다르기 때문에 PCB에는 프로세스가 <strong>어느 주소에 저장되어 있는지</strong>에 대한 정보가 저장된다.
  </li>
    <ul>
      <li>
        베이스 레지스터, 한계 레지스터, 페이지 테이블 정보가 해당한다.
      </li>
    </ul>
</ul>

<h3>1-2-6. 사용한 파일과 입출력장치 목록</h3>
<ul>
  <li>
    어떤 입출력장치가 해당 프로세스에 할당되었는지, 어떤 파일들을 열었는지에 대한 정보들이 PCB에 기록된다.
  </li>
</ul>

<br>

<h2>1-3. 문맥 교환</h2>
<ul>
  <li>
    하나의 프로세스 수행을 재개하기 위해 기억해야 할 정보를 <strong>문맥(context)</strong>이라 한다.
  </li>
    <ul>
      <li>
        PCB에 기록되는 정보들을 문맥이라 보아도 무방하다.
      </li>
    </ul>
  <li>
    프로세스가 CPU를 사용할 수 있는 시간이 다 되거나 예기치 못한 상황으로 인해 인터럼트가 발생하면 해당 프로세스의 <strong>PCB에 문백을 백업</strong>하고 새롭게 실행할 프로세스의 <strong>문백을 복원</strong>한다.
  </li>
    <ul>
      <li>
        이렇게 기존 프로세스의 문백을 PCB에 백업하고, 새로운 프로세스를 실행하기 위해 문맥을 PCB로부터 복구하여 새로운 프로세스를 실행하는 것을 <strong>문맥 교환(context switching)</strong>이라고 한다.
      </li>
    </ul>
  <li>
    문백 교환은 여러 프로세스가 끊임없이 빠르게 번갈아 수행되는 원리이다. 문맥 교환이 자주 일어나면 동시에 실행되는 것처럼 보일 수 있다.
  </li>
    <ul>
      <li>
        문맥 교환이 너무 잦은면 오버헤드가 발생할 수 있어 자주 일어난다고해서 반드시 좋은 것은 아니다.
      </li>
    </ul>
</ul>

<br>

<h2>1-4. 프로세스의 메모리 영역</h2>
<ul>
  <li>
    하나의 프로세스는 사용자 영역에 크게 <strong>코드 영역</strong>, <strong>데이터 영역</strong>, <strong>힙 영역<strong>, <strong>스택 영역</strong>으로 나뉘어 저장된다.
  </li>
</ul>

<h3>1-4-1. 코드 영역</h3>
<ul>
  <li>
    <strong>코드 영역(code segment)</strong> 혹은 <strong>텍스트 영역(text segment)</strong>라 불리는 영역은 말 그대로 실행할 수 있는 코드, 즉 <strong>기계어로 이루어진 명령어</strong>가 저장된다.
  </li>
    <li>
      코드 영역은 데이터가 아닌 CPU가 실행할 명령어가 담겨 있어 쓰기가 금지되는 <strong>읽기 전용(read-only) 공간</strong>이다.
    </li>
</ul>

<h3>1-4-2. 데이터 영역</h3>
<ul>
  <li>
    <strong>데이터 영역(data segment)</strong>은 잠깐 썼다가 없앨 데이터가 아닌 <strong>프로그램이 실행되는 동안 유지</strong>할 데이터가 저장되는 공간이다.
  </li>
    <ul>
      <li>
        대표적인 데이터로는 <strong>전역 변수(global variable)</strong>이 있다.
      </li>
    </ul>
  <li>
    <strong>코드 영역</strong>과 <strong>데이터 영역</strong>은 크기가 고정된 영역으로 <strong>정적 할당 영역</strong>이라 부르기도 한다.
  </li>
  <li>
    <strong>힙 영역</strong>과 <strong>스택 영역</strong>은 프로세스가 실행 과정에서 크기가 변할 수 있는 영역으로 <strong>동적 할당 영역</strong>이라고도 부른다.
  </li>
</ul>

<h3>1-4-3. 힙 영역</h3>
<ul>
  <li>
    <strong>힙 영역(heap segment)</strong>은 프로그램을 만드는 사용자, 즉 <strong>프로그래머</strong>가 직접 할당할 수 있는 저장 공간이다.
  </li>
    <ul>
      <li>
        프로그래밍 과정에서 힙 영역에 메모리 공간을 할당했다면 언젠가는 해당 공간을 <strong>반환</strong>해야 한다. 즉 <strong>더 이상 해당 메모리 공간을 사용하지 않는다는 것을 운영체제에 전달</strong>하는 것이다.
      </li>
    </ul>
  <li>
    메모리 공간을 반환하지 않으면 할당한 공간은 메모리 내에 계속 남아 메모리 낭비를 초래하게 되며 이런 문제를 <strong>메모리 누수(memory leak)</strong>이라 한다.
  </li>
</ul>

<h3>1-4-4. 스택 영역</h3>
<ul>
  <li>
    <strong>스택 영역(stack segment)</strong>은 데이터를 일시적으로 저장하는 공간이다.
  </li>
    <ul>
      <li>
        데이터 영역과 달리 잠깐 쓰고 처리할 값들이 저장되며 대표적인 예로 <strong>함수의 실행이 끝나면 사라지는 매개 변수</strong>와 <strong>지역 변수</strong>가 있다.
      </li>
    </ul>
  <li>
    일시저긍로 저장할 데이터는 스택 영역에 <strong>PUSH</strong>되고, 더 이상 필요하지 않은 데이터는 <strong>POP</strong>되어 스택 영역에서 사라진다.
  </li>
  <li>
    힙 영역과 스택 영역은 실시간으로 크기가 변할 수 있어 <strong>동적 할당 영역</strong>이라 한다.
  </li>
  <li>
    일반적으로 힙 영역은 메모리의 <strong>낮은 주소에서 높은 주소</strong>로 할당되고, 스택 영역은 <strong>높은 주소에서 낮은 주소</strong>로 할당된다. 이유는 <strong>서로 겹치는 일이 없게</strong> 하기 위해서이다.
  </li>
</ul>

<br><br>

<h1>2. 프로세스 상태와 계층 구조</h1>
<h2>2-1. 프로세스 상태</h2>
<ul>
  <li>
    컴퓨터를 사용할 때 여러 프로세스들이 빠르게 번갈아 가며 실행되며 이로 인하여 하나의 프로세스는 <strong>여러 상태</strong>를 거치며 실행된다.
  </li>
  <li>
    운영체제는 프로세스의 상태를 <strong>커널 영역 메모리</strong>의 <strong>PCB</strong>를 통해 인식하고 관리한다.
  </li>
  <li>
    프로세스의 상태를 표현하는 방식은 운영체제마다 조금씩 차이가 있다.
  </li>
  <li>
    각 상태를 도표로 나타낸 것을 <strong>프로세스 상태 다이어그램(process state diagram)</strong>이라 한다.
  </li>
    <ul>
      <li>
        운영체제는 이 상태를 PCB에 기록하여 프로세스들을 관리한다.
      </li>
    </ul>
</ul>

<h3>2-1-1. 생성 상태</h3>
<ul>
  <li>
    프로세스를 생성 중인 상태를 <strong>생성 상태(new)</strong>라고 한다. 즉 <strong>이제 막 메모리에 적재</strong>되어 PCB를 할당 받은 상태이다.
  </li>
  <li>
    생성 상태를 거쳐 실행할 준비가 완료된 프로세스는 곧바로 실행되지 않고 <strong>준비 상태로 CPU의 할당을 기다린다</strong>.
  </li>
</ul>

<h3>2-1-2. 준비 상태</h3>
<ul>
  <li>
    준비 상태(ready)는 당장 CPU를 할당받아 <strong>실행할 준비</strong>는 되어 있으나 아직 차례가 되지 않아 <strong>대기중인 상태</strong>를 의미한다.
  </li>
  <li>
    준비 상태인 프로세스가 실행 상태로 전환되는 것을 <strong>디스패치(dispatch)</strong>라고 한다.
  </li>
</ul>

<h3>2-1-3. 실행 상태</h3>
<ul>
  <li>
    실행 상태(running)는 CPU를 할당받아 <strong>실행 중인 상태</strong>를 의미한다.
  </li>
  <li>
    실행 상태인 프로세스는 <strong>할당된 일정 시간</strong> 동안만 CPU를 사용할 수 있다.
  </li>
    <ul>
      <li>
        프로세스에 할당된 시간을 모두 사용하는 경우(타이머 인터럽트 발생) 다시 <strong>준비 상태</strong>가 된다.
      </li>
    </ul>
  <li>
    실행 도중 <strong>입출력장치</strong>를 사용하여 입출력장치의 작업이 끝날 때까지 기다려야 한다면 <strong>대기 상태</strong>가 된다.
  </li>
</ul>

<h3>2-1-4. 대기 상태</h3>
<ul>
  <li>
    <strong>입출력 작업</strong>은 CPU에 비해 처리 속도가 느리기 때문에 입출력을 요청한 프로세스는 입출력장치가 입출력을 끝낼 때까지 기다리게 되며 이 상태를 <strong>대기 상태(blocked)</strong>라 한다.
  </li>
  <li>
    입출력 작업이 완료되면 해당 프로세스는 다시 <strong>준비 상태</strong>로 CPU 할당을 기다린다.
  </li>
  <li>
    입출력 작업만 해당하는 것은 아니며 <strong>특정 이벤트가 일어나길 기다릴 때</strong>가 해당한다.
  </li>
</ul>

<h3>2-1-5. 종료 상태</h3>
<ul>
  <li>
    종료 상태(terminated)는 프로세스가 종료된 상태이다.
  </li>
  <li>
    프로세스가 종료되면 운영체제와 <strong>PCB와 프로세스가 사용한 메모리를 정리</strong>한다.
  </li>
</ul>

<br>

<h2>2-2. 프로세스 계층 구조</h2>
<ul>
  <li>
    프로세스는 실행 도중 시스템 호출을 통해 <strong>다른 프로세스를 생성</strong>할 수 있으며 이때 새 프로세스를 생성한 프로세스를 <strong>부모 프로세스(parent process)</strong>, 부모 프로세스에 의해 생성된 프로세스를 <strong>자식 프로세스(child process)</strong>라 한다.
  </li>
    <ul>
      <li>
        부모 프로세스와 자식 프로세스는 엄연히 다른 프로세스이기에 <strong>각기 다른 PID</strong>를 가진다.
      </li>
        <ul>
          <li>
            일부 운영체제에서는 자식 프로세스의 PCB에 부모 프로세스의 PID인 <strong>PPID(Parent PID)</strong>가 기록되기도 한다.
          </li>
        </ul>
    </ul>
  <li>
    자식 프로세스는 또 다른 자식 프로세스를 생성할 수 있으며 이는 계속해서 반복될 수 있다. 많은 운영체제는 이와 같은 <strong>프로세스의 계층 구조</strong>로 프로세스를 관리한다.
  </li>
  <li>
    프로세스의 계층 구조를 트리 구조로 나타낼 수 있고 이를 <strong>프로세스 계층 구조(p299)</strong>라 한다.
  </li>
</ul>

<h4>최초의 프로세스</h4>
<ul>
  <li>
    모든 프로세스에서 가장 위에 있는 프로세스가 최초의 프로세스이다.
  </li>
    <ul>
      <li>
        유닉스 운영체제에서는 init, 리눅스 운영체제에서는 systemd, macOS에서는 launchd라고 한다.
      </li>
      <li>
        최초의 프로세스 PID는 항상 1번이며, 모든 프로세스의 최상단에 있는 부모 프로세스이다.
      </li>
    </ul>
</ul>

<br>

<h2>2-3. 프로세스 생성 기법</h2>
<ul>
  <li>
    부모 프로세스는 <strong>fork</strong>를 통해 자신의 <strong>복사본</strong>을 자식 프로세스로 생성한다.
  </li>
    <ul>
      <li>
        만들어진 복사본(자식 프로세스)은 <strong>exec</strong>를 통해 자신의 메모리 공간을 <strong>다른 프로그램으로 교체</strong>한다.
      </li>
    </ul>
  <li>
    fork와 exec는 시스템 호출이다. 부모 프로세스는 <strong>fork 시스템 호출</strong>을 통해 자신의 복사본을 자식 프로세스로 만든다.
  </li>
    <ul>
      <li>
        이때 부모 프로세스의 자원들인 메모리 내용, 열린 파일 목록 등이 상속된다. (단, PID 값이나 저장된 메모리 위치는 다르다.).
      </li>
      <li>
        exec는 이렇게 만들어진 자식 프로세스의 메모리 공간을 <strong>새로운 프로그램으로 덮어쓰는</strong> 시스템 호출이다.
      </li>
    </ul>
  <li>
    예를 들면 다음이 있다.
  </li>
    <ul>
      <li>
        사용자가 bash 셸에서 ls라는 명령어를 입력한다.
        <br>→ 셸 프로세스는 fork를 통해 자신과 동일한 프로세스를 생성한다.
        <br>→ 이렇게 탄생한 자식 프로세스는 exec를 통해 ls 명령어를 실행하기 위한 프로세스로 전환되어 실행된다.
        <br>→ 자식 프로세스는 ls 명령어를 실행하기 위한 프로세스로 바뀐다.
        <br>→ 메모리 공간은 ls 명령어를 싱행하기 위한 내용들로 채워진다.
      </li>
    </ul>
  <li>
    부모 프로세스가 자식 프로세스를 fork한 뒤에 부모 프로세스와 자식 프로세스 <strong>누구도 exec를 호출하지 않는 경우</strong>도 있으며 이때는 부모와 자식 프로세스는 <strong>같은 코드를 병행</strong>하여 실행하는 프로세스가 된다.
  </li>
</ul>

<br><br>

<h1>3. 스레드</h1>
<h2>3-1. 프로세스와 스레드</h2>
<ul>
  <li>
    실행의 흐름 단위가 하나로 실행되는 프로세스들은 <strong>단일 스레드 프로세스</strong>라고 볼 수 있다.
  </li>
  <li>
    <strong>스레드</strong>라는 개념이 도입되면서 하나의 프로세스가 <strong>여러 일을 동시에 처리</strong>할 수 있게 되었다. 즉 <strong>여러 명령어를 동시에 실행</strong>할 수 있게 된 것이다.
  </li>
  <li>
    스레드는 프로세스 내에서 각기 다른 스레드 ID, 프로그램 카운터 값을 비롯해 레지스터 값, 스택으로 구성된다.
  </li>
    <ul>
      <li>
        각자 프로그램 카운터 값을 비롯한 레지스터 값, 스택을 가지고 있어 스레드마다 다른 코드를 실행할 수 있다.
      </li>
    </ul>
  <li>
    중요한 점은 스레드들이 실행에 필요한 최소한의 정보만을 유지하기 위해 <strong>프로세스 자원을 공유하며 실행</strong>된다는 점이다.
  </li>
    <ul>
      <li>
        프로세스가 실행되는 프로그램이라 본다면 스레드는 <strong>프로세스를 구성하는 실행의 흐름 단위</strong>이다.
      </li>
    </ul>
</ul>

<h4>리눅스 운영체제에서 프로세스 vs 스레드</h4>
<ul>
  <li>
    리눅스는 프로세스와 스레드를 모두 실행의 문맥(context of execution)이라는 점에서 동등하다고 간주하며 둘을 크게 구분짓지 않는다. 따라서 프로세스와 스레드라는 말 대신 <strong>태스크(task)라는 이름으로 통일하여 명명</strong>한다.
  </li>
</ul>

<br>

<h2>3-2. 멀티프로세스와 멀티스레드</h2>
<ul>
  <li>
    여러 프로세스를 동시에 실행하는 것을 <strong>멀티프로세스(multiprocess)</strong>, 그리고 여러 스레드로 프로세스를 동시에 실행하는 것을 <strong>멀티스레드(multithread)</strong>라 한다.
  </li>
  <li>
    일반적으로 멀티프로세스는 멀티스레드와 같이 <strong>메모리(프로세스의 자원)</strong>를 공유하지 않기 때문에 fork를 하며 <strong>메모리의 낭비가 더 크다는 단점</strong>이 있다.
  </li>
    <ul>
      <li>
        멀티프로세스에서 fork를 한 직후 같은 프로세스를 통째로 메모리에 중복 저장하지 않으면서 동시에 프로세스끼리 자원을 공유하지 않는 방법도 존재하는데 이를 <strong>쓰기 시 복사(copy on write) 기법</strong>이라한다.
      </li>
      <li>
        멀티스레드는 자원을 공유한다는 장점이 있지만 반대로 하나의 스레드에 문제가 생기면 <strong>자원을 공유하는 모든 스레드</strong>가 영향을 받는다는 단점도 있다.
      </li>
    </ul>
</ul>

<h4>프로세스 간 통신</h4>
<ul>
  <li>
    기본적으로 프로세스간에는 자원을 공유하지 않지만 프로세스끼리도 충분히 자원을 공유하고 데이터를 주고받을 수 있으며 이를 <strong>프로세스 간 통신(IPCl Inter-Process Communication)</strong>이라 부른다.
  </li>
    <ul>
      <li>
        예를 들어 프로세스 A는 'hello.txt' 파일에 새로운 값는 프로세스, 프로세스 B는 'hello.txt' 파일을 읽는 프로세스라 한다면 이는 <strong>파일을 통한 프로세스 간 통신</strong>으로 볼 수 있다.
      </li>
    </ul>
  <li>
    프로세스들은 서로 공유하는 메모리 영역을 두어 데이터를 주고 받을 수 있으며 이러한 메모리 영역을 <strong>공유 메모리(shared memory)</strong>라 한다.
  </li>
  <li>
    이외에도 소켓, 파이프 등을 통해 프로세스 간 통신이 가능하며 따라서 스레드에 비해 다소 까다로운 것일 뿐 불가능하지는 않다는 것을 알 수 있다.
  </li>
</ul>
